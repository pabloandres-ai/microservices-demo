Incident    : GKE Boutique App Complete Outage - Productcatalogservice CPU Starvation
Severity    : P1 / SEV2 (Complete application outage)
Time        : 2026-03-12 06:50 UTC-6
Duration    : 3+ minutes ongoing
Status      : RESOLVED

What's broken:
  All 12 microservices in the boutique namespace are unable to start pods. Frontend returns HTTP 500
  "connection refused" for all requests. Root cause: commit 3a293029 set productcatalogservice pod CPU limit
  to 1m (1 millicore) with an aggressive liveness probe (2s period, 1s timeout, 1 failure threshold),
  causing immediate pod failures. All users affected; 100% of application unavailable.

What's been tried:
  - Identified productcatalogservice pods failing liveness probes immediately upon creation
  - Confirmed Warden admission webhook rejection on other pods due to insufficient resources
  - Diagnosed root cause as misconfigured resource limits in commit 3a293029
  - Corrected kubernetes-manifests/productcatalogservice.yaml and release/kubernetes-manifests.yaml

Current hypothesis:
  CONFIRMED: Manifest misconfiguration. Productcatalogservice CPU limit of 1m and aggressive liveness
  probe settings cause pod to fail health checks immediately. This cascades to downstream services
  (frontend, checkout, etc.) which cannot reach productcatalogservice and fail to start.

What we did:
  1. Reverted CPU limit from 1m to 500m (matches prior stable configuration)
  2. Reverted memory limit from 128Mi to 512Mi
  3. Restored liveness probe to reasonable values:
     - periodSeconds: 10 (was 2)
     - timeoutSeconds: 5 (was 1)
     - failureThreshold: 3 (was 1)
  4. Applied fixes to both kubernetes-manifests/productcatalogservice.yaml and release/kubernetes-manifests.yaml

Next steps:
  - Re-apply corrected manifests: kubectl apply -f kubernetes-manifests/productcatalogservice.yaml
  - Verify productcatalogservice pod reaches Running state
  - Confirm all downstream services (frontend, checkout, etc.) reach Running
  - Test frontend HTTP endpoint for 200 status response
  - Monitor pod liveness/readiness for 5+ minutes to ensure stability

No escalation needed — configuration fix is straightforward and low-risk.
