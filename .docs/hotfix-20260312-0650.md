# fix(ops): revert productcatalogservice CPU starvation from commit 3a293029

## Problem

Commit 3a293029 introduced a misconfigured resource limit (1m CPU) and aggressive liveness probe (2s period, 1s timeout, 1 failure threshold) to the productcatalogservice Deployment in production. This caused:

- **Immediate liveness probe failures** — the pod cannot execute a gRPC health check in 1 second with only 1m CPU allocated
- **Complete restart loop** — pod dies, restarts, fails again within ~2 seconds
- **Cascade failure** — frontend, checkout, and all dependent services cannot reach productcatalogservice and fail to start
- **Complete application outage** — all 12 microservices unable to start; frontend HTTP 500 for all user requests
- **Duration:** 3+ minutes (2026-03-12 06:50–06:55 UTC-6)
- **User impact:** 100% of users; all features unavailable

---

## Root Cause

Commit 3a293029 appears to be a debug/test configuration that was accidentally merged into the production branch without:
1. Code review validation
2. CI/CD pre-deployment manifest validation
3. Awareness that 1m CPU is below GKE Autopilot's minimum viable limit

The aggressive liveness probe (periodSeconds: 2) combined with insufficient CPU to execute the health check creates an immediate failure condition.

---

## Fix

Revert resource limits and liveness probe settings to the last known stable configuration (commit 27223c87):

**Changes:**
1. `kubernetes-manifests/productcatalogservice.yaml`:
   - CPU limit: 1m → 500m
   - Memory limit: 128Mi → 512Mi
   - Liveness probe: periodSeconds 2 → 10, timeoutSeconds 1 → 5, failureThreshold 1 → 3

2. `release/kubernetes-manifests.yaml`:
   - Identical changes to the auto-generated release manifest

**Testing:**
- Applied corrected manifest to prod cluster
- Productcatalogservice pod reached Running state within 30 seconds
- Liveness/readiness probes passing consistently
- Frontend pod creation unblocked
- All 12 services reached Running
- Frontend HTTP 200 verified across all endpoints
- No connection errors in logs

## Prevention (Follow-up)

This incident was preventable with:
1. **CI/CD manifest validation** — reject CPU limits < 100m
2. **Kubernetes linting** — `kubeval` or Kyverno policy enforcement
3. **Code review checklist** — explicit sign-off on resource limit changes
4. **Staged deployment** — dry-run manifest validation in pre-prod before prod apply
5. **Runbook documentation** — GKE Autopilot minimum requirements (CPU >= 100m, memory >= 128Mi)
