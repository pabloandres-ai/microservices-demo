## Summary

All 12 microservices in the boutique namespace failed to start on GKE Autopilot at 2026-03-12 06:50 UTC-6, causing a complete application outage lasting 3+ minutes. Frontend returned HTTP 500 "connection refused" for all user requests. Root cause: commit 3a293029 misconfigured the productcatalogservice Deployment with a 1m (1 millicore) CPU limit and an aggressive liveness probe (2s period, 1s timeout, 1 failure threshold), causing immediate pod failures.

---

## Root Cause

Commit 3a293029 ("updated kubernetes-manifests/productcatalogservice.yaml and release/kubernetes-manifests.yaml with an extremely low CPU limit of 1m and an aggressive LivenessProbe...") introduced a test/debug configuration into production manifests:

**Before (commit 27223c87):**
```yaml
resources:
  requests:
    cpu: 100m
    memory: 64Mi
  limits:
    cpu: 500m
    memory: 512Mi
livenessProbe:
  initialDelaySeconds: 10
  periodSeconds: 10
  timeoutSeconds: 5
  failureThreshold: 3
  grpc:
    port: 3550
```

**Broken (commit 3a293029):**
```yaml
resources:
  requests:
    cpu: 1m
    memory: 64Mi
  limits:
    cpu: 1m
    memory: 128Mi
livenessProbe:
  initialDelaySeconds: 10
  periodSeconds: 2
  timeoutSeconds: 1
  failureThreshold: 1
  grpc:
    port: 3550
```

With 1m CPU allocated, the productcatalogservice container cannot execute gRPC health checks within the 1-second timeout window. The liveness probe fails immediately (after ~2 seconds), triggering a restart loop. This cascades to dependent services (frontend, checkout, payment, etc.) which cannot reach productcatalogservice and also fail to start.

## Resolution

Reverted resource limits and liveness probe settings in both `kubernetes-manifests/productcatalogservice.yaml` and `release/kubernetes-manifests.yaml`:

**CPU limit:** 1m → 500m
**Memory limit:** 128Mi → 512Mi
**Liveness probe periodSeconds:** 2 → 10
**Liveness probe timeoutSeconds:** 1 → 5
**Liveness probe failureThreshold:** 1 → 3

Commands executed:
```bash
# Apply corrected manifest to prod cluster
kubectl apply -f kubernetes-manifests/productcatalogservice.yaml -n boutique

# Verify pod recovery
kubectl get pods -n boutique -l app=productcatalogservice
kubectl logs -n boutique deployment/productcatalogservice -c server --tail=50
```

## Prevention

**Root cause:** Commit 3a293029 appears to be a debug/test change that was accidentally merged without:
1. Code review validation of resource limits
2. CI/CD pipeline checks for manifests with CPU < 100m
3. Pre-deployment manifest linting in the release pipeline

**Preventive measures:**
1. **CI/CD gate:** Add manifest validation step that rejects any Deployment/StatefulSet with `limits.cpu < 100m` or `limits.cpu < requests.cpu`
2. **Manifest linting:** Integrate `kubeval`, `kube-score`, or Kyverno policy to enforce GKE Autopilot requirements in CI
3. **Code review checklist:** Require explicit acknowledgment of resource limit changes in all manifest PRs
4. **Staged deployment:** Use `kubectl diff` or Kyverno dry-run in pre-prod cluster before applying to prod
5. **Runbook update:** Document minimum resource requirements for GKE Autopilot (CPU >= 100m limit, memory >= 128Mi)
